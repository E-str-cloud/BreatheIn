# ARCHITECTURE.md
# ארכיטקטורה טכנית — „נשום פנימה” (Breathe In)

## 1. מטרת המסמך

מסמך זה מתאר את הארכיטקטורה הטכנית למימוש האפליקציה „נשום פנימה” בהתאם לדרישות ה־PRD ולהחלטות ה־Technology Stack. הוא מיועד לשמש מקור אמת למערכת AI או למפתחים שיממשו את המוצר.

המסמך מגדיר את מבנה המערכת, רכיבי ה־Frontend, התנהגות האודיו, תמיכה ב־PWA ובעבודה Offline, פריסה, אבטחה, בדיקות והחלטות טכניות מרכזיות.

## 2. סתירות בין ה־PRD ל־Technology Stack

לא זוהתה סתירה מהותית בין דרישות המוצר לבין ה־Technology Stack.

ה־PRD מתאר אפליקציה קטנה, ללא משתמשים או מידע אישי, שצריכה לפעול Offline לאחר טעינה ראשונה ולהשמיע ארבעה קטעי אודיו קצרים. ה־Technology Stack שנבחר תומך בכך באמצעות Frontend סטטי, קובצי אודיו מקומיים ו־PWA.

אף שהבקשה למסמך הארכיטקטורה מזכירה Backend, Database ו־APIs, אין דרישה מוצרית שמצדיקה רכיבים אלה בגרסה הנוכחית. לכן הם אינם נכללים במימוש: אין להוסיף אותם רק כדי למלא סעיף במסמך. אם יתווספו בעתיד חשבונות משתמשים, שמירת מידע בענן או יכולת ניהול תוכן מרחוק, יש לבחון מחדש את הארכיטקטורה.

## 3. תקציר הארכיטקטורה

המערכת תהיה אפליקציית Web סטטית, Client-side, המבוססת על React ו־TypeScript, נבנית באמצעות Vite ומוגדרת כ־Progressive Web App (PWA).

- **Frontend:** React + TypeScript + Vite.
- **עיצוב:** CSS פשוט או CSS Modules; ללא ספריית UI כבדה.
- **ניווט:** שני מסכים בלבד — מסך בית ומסך פעולה — ללא צורך ב־Router חיצוני.
- **אודיו:** ארבעה קובצי אודיו מקומיים, המופעלים דרך HTML Audio API.
- **Offline/PWA:** `vite-plugin-pwa` ו־Workbox לצורך Web App Manifest, Service Worker ושמירת משאבי האפליקציה ב־Cache.
- **Hosting:** Cloudflare Pages. ניתן להשתמש ב־GitHub Pages כחלופה, בכפוף להגדרת נתיבי הפריסה.
- **Version Control:** Git ו־GitHub.
- **בדיקות:** Vitest לבדיקות יחידה ו־Playwright לבדיקות זרימות משתמש בדפדפן.
- **Backend / Database / Authentication / API:** לא נדרשים.
- **מידע אישי ו־Analytics:** לא נאספים בגרסה זו.

זרימת הבקשה בזמן ריצה:

1. הדפדפן טוען את קובצי האפליקציה מה־Hosting.
2. ה־Service Worker שומר את משאבי האפליקציה ואת קובצי האודיו ב־Cache בהתאם למדיניות שנקבעה.
3. לאחר שהמשאבים נשמרו בהצלחה, האפליקציה יכולה להיפתח ללא חיבור לרשת.
4. React מנהל את מצב המסך ואת בחירת האודיו בתוך הדפדפן.
5. הדפדפן מנגן את קובץ האודיו המקומי; לא נדרשת בקשת רשת לצורך ההשמעה.

## 4. מבנה רכיבים

מבנה מוצע:

```text
src/
  app/
    App.tsx
    appState.ts
  components/
    AppHeader.tsx
    PrimaryButton.tsx
    AudioRetryControl.tsx
  features/
    home/
      HomeScreen.tsx
    action/
      ActionScreen.tsx
      soundCatalog.ts
      audioController.ts
  styles/
    global.css
    tokens.css
  assets/
    sounds/
      fart.mp3
      burp.mp3
      bouncy-cartoon.mp3
      boing.mp3
  types/
    audio.ts
public/
  icons/
  manifest.webmanifest
  (משאבים סטטיים נוספים לפי הצורך)
```

זהו מבנה לוגי מומלץ ולא דרישה לשמות קבצים מדויקים. אפשר לשנות שמות או לאחד קבצים כאשר הדבר מפשט את המימוש, אך יש לשמור על הפרדה ברורה בין תצוגה, לוגיקת האודיו, הגדרות ה־PWA והמשאבים הסטטיים.

### 4.1 `App`

- מחזיק את מצב הניווט בין `home` ל־`action`.
- מציג מסך אחד בכל פעם.
- אינו דורש ספריית Routing חיצונית.
- המעבר הוא חד־כיווני: מ־`home` ל־`action` בלבד. אין חזרה למסך הבית; הוא מוצג רק בפתיחה מחדש של האפליקציה.
- אינו משמיע אודיו בטעינת מסך הבית.

### 4.2 `HomeScreen`

- מציג את שם האפליקציה „נשום פנימה” ואת כפתור `Enter`.
- שומר על העיצוב המינימליסטי והרגוע שהוגדר ב־PRD וב־Style Guide.
- אינו מציג דמויות, איורים הומוריסטיים או הסברים נוספים.
- בלחיצה על `Enter`, מעביר למסך הפעולה ומבקש להפעיל אוטומטית את צליל הפלוץ.

### 4.3 `ActionScreen`

- מציג כפתור `Start` ועיגול עם סמל Play במרכז הטבעות. אין בו כפתור `Home` או קישור למסך הבית.
- העיגול עם סמל ה־Play הוא אלמנט `button` שמפעיל את אותו handler של `Start` בדיוק.
- בכניסה למסך הפעולה מתבצע ניסיון להשמיע את צליל הפלוץ.
- כל לחיצה על `Start` בוחרת באקראי צליל אחד מתוך כל ארבעת הצלילים.
- מותר שאותו צליל ייבחר ברציפות; אין מנגנון למניעת חזרות.
- אין להוסיף טקסטים או פעולות שלא הוגדרו ב־PRD.
- אם השמעה נכשלת בגלל מגבלת דפדפן או תקלה, מוצג `AudioRetryControl`: כפתור עגול קטן עם אייקון רמקול מושתק, ללא טקסט גלוי, עם `aria-label="הפעלת קול"`. לחיצה עליו קוראת ל־`retryLastSound()`, והוא מוסתר לאחר השמעה מוצלחת.

### 4.4 `soundCatalog`

קטלוג יחיד של ארבעת הצלילים, עם מזהה יציב ונתיב לקובץ מקומי:

1. `fart` — צליל פלוץ.
2. `burp` — גיהוק.
3. `bouncy-cartoon` — צליל קפיצי מצויר.
4. `boing` — צליל בוינג.

כל קטע אודיו יהיה באורך של עד שתי שניות. יש לוודא שלכל קובץ יש רישיון מתאים לשימוש באפליקציה. יש להשתמש בקובצי אודיו מקומיים בלבד, ולא בכתובות URL של שירותים חיצוניים.

### 4.5 `audioController`

אחראי על הפעלת אודיו, טיפול בשגיאות וניסיון חוזר. עליו לספק ממשק פשוט כגון:

- `playSound(soundId)` — השמעת צליל לפי מזהה.
- `playEntrySound()` — ניסיון להשמיע את צליל הפלוץ בכניסה למסך הפעולה.
- `retryLastSound()` — ניסיון חוזר לאחר כישלון השמעה.

אלה שמות API פנימיים מוצעים בלבד, ולא APIs חיצוניים.

יש למנוע חפיפה לא מכוונת בין השמעות: לפני התחלת צליל חדש יש לעצור או לאפס השמעה קודמת, בהתאם להתנהגות שתיבחר במימוש. אין צורך במיקסר, ניהול ערוצים או ספריית אודיו חיצונית.

## 5. Frontend וטכנולוגיות

### 5.1 React + TypeScript

React מתאים לניהול שני מסכים ורכיבי UI פשוטים. TypeScript מספק בדיקת טיפוסים ומקטין טעויות במזהי צלילים, מצב המסך ופעולות האודיו. Vite מספק סביבת פיתוח ו־Build סטטי מהירה.

אין צורך ב־Next.js או ב־SSR: האפליקציה אינה דורשת SEO מורכב, תוכן דינמי מהשרת או יצירת דפים בצד השרת.

### 5.2 CSS

יש להשתמש ב־CSS רגיל או ב־CSS Modules. הבחירה המועדפת היא הפתרון הפשוט ביותר לצוות המממש. יש לרכז צבעים, מרווחים, רדיוסים, טיפוגרפיה וערכי עיצוב חוזרים ב־`tokens.css` או בקובץ דומה.

אין צורך בספריית UI רחבה או במערכת עיצוב חיצונית. יש לממש את ה־Style Guide וה־Mockups שסופקו, ולא להמציא רכיבים או טקסטים נוספים.

### 5.3 שפה וכיווניות

- שפת הממשק: עברית.
- כיווניות: RTL.
- יש להגדיר `lang="he"` ו־`dir="rtl"` באלמנט `html`.
- יש לבדוק יישור, סדר רכיבים, פוקוס מקלדת ומיקום אייקונים במצב RTL.
- שם המוצר באנגלית, `Breathe In`, יכול להופיע רק במקומות שהוגדרו בעיצוב.

### 5.4 Responsive

היישום יהיה Mobile-first ויתאים למסכים צרים ולמסכי Desktop. יש להימנע מרוחבים קשיחים שעלולים לגרום לגלילה אופקית. כפתורי הפעולה צריכים להיות נוחים ללחיצה במכשירי מגע.

## 6. לוגיקת המוצר ומצבי האפליקציה

מצבי המסך:

- `home` — מסך הבית.
- `action` — מסך הפעולה.

מצבי אודיו פנימיים מוצעים:

- `idle` — אין השמעה פעילה.
- `playing` — מתבצעת השמעה.
- `blocked` — הדפדפן דחה את ניסיון ההשמעה או שההשמעה לא התחילה.
- `error` — אירעה שגיאת אודיו אחרת.

מצבים אלה נועדו לשלוט בהתנהגות הממשק בלבד; אין צורך לשמור אותם בשרת או ב־Database.

### 6.1 התנהגות `Enter`

1. המשתמש לוחץ על `Enter`.
2. האפליקציה עוברת למסך הפעולה.
3. מתבצע ניסיון להשמיע את קובץ `fart` המקומי.
4. אם ההשמעה מתחילה, אין צורך להציג הודעה.
5. אם `play()` נדחה או שההשמעה נכשלת, האפליקציה מציגה אפשרות עדינה לנסות שוב, ללא הודעת שגיאה טכנית בולטת.

לחיצה על כפתור יכולה לשמש מחוות משתמש (user gesture), אך אין להבטיח שכל דפדפן יאשר השמעה בכל מצב. יש לטפל בדחיית Promise שמוחזרת מ־`HTMLMediaElement.play()`.

### 6.2 התנהגות `Start`

1. בוחרים פריט אקראי מתוך כל ארבעת הפריטים ב־`soundCatalog`.
2. מפעילים את הקובץ המקומי שנבחר.
3. אין להחריג את הצליל האחרון ואין למנוע חזרה על אותו צליל.
4. אם ההשמעה נכשלת, יש לאפשר ניסיון חוזר באופן עדין.

### 6.3 חזרה למסך הבית

- אין חזרה למסך הבית מתוך האפליקציה ואין כפתור `Home`.
- מסך הבית מוצג רק בפתיחה מחדש של האפליקציה (או בטעינה מחדש של הדף).

## 7. אודיו

### 7.1 פורמט ואחסון

- קובצי האודיו יהיו חלק מה־Build הסטטי של האפליקציה.
- מומלץ להשתמש ב־MP3 לצורך תאימות רחבה, לאחר בדיקת איכות הצליל וגודל הקבצים.
- שמות הקבצים צריכים להיות קבועים ומנורמלים.
- יש להימנע מטעינת אודיו מ־CDN או משירות חיצוני בזמן ריצה.
- יש לכלול את הקבצים הנדרשים ב־Precache כדי שיהיו זמינים Offline לאחר התקנה/טעינה מלאה.

### 7.1.1 אספקת הקבצים ותיעוד המקור

- את ארבעת הקבצים מורידה בעלת המוצר מ־Pixabay (או מ־Mixkit כחלופה), בהתאם ל־PRD סעיף 4.3. ה־AI אינו מוריד או יוצר קובצי אודיו.
- הקבצים יישמרו בתיקייה `src/assets/sounds/` בשמות הקבועים הבאים: `fart.mp3`, `burp.mp3`, `bouncy-cartoon.mp3`, `boing.mp3`.
- מקור כל קובץ יתועד בקובץ `src/assets/sounds/SOURCES.md`: שם הקובץ, קישור לדף הצליל, שם היוצר והרישיון.
- קובץ שאורכו עולה על שתי שניות יקוצר בעת המימוש; בנוסף, `audioController` יעצור כל השמעה בתום שתי שניות.
- הבדלי עוצמה בין הקבצים יאוזנו בעת המימוש באמצעות ערך עוצמה (`volume`) לכל צליל ב־`soundCatalog`, ללא עריכה ידנית של הקבצים.
- אין להתחיל את Milestone 2 לפני שארבעת הקבצים נמצאים בתיקייה.

### 7.2 טיפול בהשמעה

יש להשתמש ב־HTML Audio API, ללא ספריית אודיו נוספת. יש לטפל לפחות במצבים הבאים:

- `play()` נדחה עקב מדיניות autoplay.
- הקובץ לא נטען או נכשל בפענוח.
- המשתמש לוחץ שוב בזמן שצליל קודם עדיין מתנגן.

יש להציג למשתמש רק ממשק התאוששות קטן ורלוונטי, לא stack trace או הודעת שגיאה טכנית.

## 8. PWA ו־Offline

### 8.1 רכיבים

- `vite-plugin-pwa` ליצירת קובצי PWA ולחיבור ל־Workbox.
- Web App Manifest עם שם האפליקציה, שם קצר, צבעי ממשק, `start_url`, `scope`, `display: standalone` ואייקונים.
- Service Worker לשמירת קובצי ה־Build והאודיו ב־Cache.
- HTTPS בסביבת Production; Service Workers דורשים secure context, למעט סביבת localhost לפיתוח.

### 8.2 מדיניות Cache

מכיוון שכל התוכן סטטי ואינו אישי, יש להעדיף מדיניות פשוטה:

- **App shell ומשאבי Build:** Precache בזמן התקנת ה־Service Worker.
- **קובצי אודיו:** Precache יחד עם יתר המשאבים, או לכלול אותם ברשימת משאבים סטטיים מפורשת.
- **בקשות רשת חיצוניות:** אין צורך בבקשות כאלה בזמן ריצה.
- **מידע משתמש:** לא קיים ולכן אין צורך ב־Cache ייעודי או בסנכרון.

יש לוודא שכל ארבעת קובצי האודיו אכן נשמרים ב־Cache, ולא להניח זאת רק משום שהם נמצאים בתיקיית `src/assets`. יש לבדוק את תוצאת ה־Build ואת התנהגות האפליקציה לאחר התקנה.

### 8.3 עדכונים

בעת פרסום גרסה חדשה, ה־Service Worker צריך לזהות את המשאבים החדשים ולעדכן את ה־Cache. יש להשתמש בהתנהגות עדכון צפויה ופשוטה, ללא מסך עדכון מורכב. יש להימנע ממצב שבו קובצי JavaScript מגרסה אחת מתייחסים לקובצי אודיו שאינם זמינים ב־Cache.

### 8.4 גבולות Offline

- נדרש חיבור רשת לצורך ביקור ראשון והורדת המשאבים.
- לאחר שהמשאבים נשמרו בהצלחה, האפליקציה אמורה להיפתח ולהשמיע את הצלילים Offline.
- התקנה אינה זהה בכל הדפדפנים ומערכות ההפעלה; אפשר להשתמש באפליקציה גם כאתר PWA בדפדפן תומך.
- אין להבטיח Offline לפני שההתקנה/הטעינה הראשונית הסתיימה וה־Cache הושלם.

## 9. Backend, Database ו־APIs

### 9.1 Backend

לא נדרש Backend. כל הלוגיקה העסקית מצומצמת לניווט בין שני מסכים, בחירת צליל אקראי וניגון קובץ מקומי. הוספת שרת תגדיל מורכבות, עלות ושטח תקיפה ללא תועלת לדרישות הנוכחיות.

### 9.2 Database

לא נדרש Database. אין חשבונות משתמשים, העדפות שצריך לסנכרן, היסטוריית שימוש, תוכן דינמי או מידע אישי לשמירה.

אין להשתמש ב־localStorage או ב־IndexedDB לצורך נתוני מוצר, אלא אם תתווסף בעתיד דרישה מפורשת. ה־Cache של ה־Service Worker הוא מטמון משאבים טכני, לא Database של המוצר.

### 9.3 APIs

אין צורך ב־External APIs או ב־API פנימי. כל המשאבים מוגשים כקבצים סטטיים. יש להימנע מתלות בזמן ריצה בשירותי צד שלישי, כולל שירותי אודיו, Analytics או AI.

## 10. תשתיות Cloud ופריסה

### 10.1 Hosting

ברירת המחדל היא Cloudflare Pages, המיועד לאירוח אתרים סטטיים ותומך בפריסה מתוך Git. הוא מתאים למוצר ללא Backend, עם קובצי Build סטטיים ו־HTTPS.

חלופה: GitHub Pages. אם משתמשים בו, יש להגדיר נכון את `base` ב־Vite כאשר האפליקציה מוגשת מתת־נתיב ולא משורש הדומיין.

תנאי התוכנית החינמית, מגבלות הבנייה והאחסון עשויים להשתנות; יש לבדוק אותם בעת הפריסה. אין צורך בשרת ייעודי, Container, Kubernetes או שירות Database.

### 10.2 Build ו־Deploy

- פקודת Build של Vite יוצרת את התוצרים הסטטיים בתיקיית `dist/`.
- פלט `dist/` הוא התוכן שיש לפרסם ב־Hosting.
- יש להגדיר את פקודת Build ואת תיקיית הפלט בהתאם לספק.
- יש לוודא שה־Manifest, ה־Service Worker, האייקונים וקובצי האודיו נכללים בתוצר.
- אין לשמור מפתחות סודיים או credentials בקוד Frontend. בגרסה זו אין צורך ב־secrets.

### 10.3 Domain ו־HTTPS

אפשר להשתמש בדומיין שסופק על ידי שירות ה־Hosting או לחבר דומיין מותאם אישית. דומיין מותאם אישית עשוי להיות כרוך בעלות. Production חייב להיות מוגש ב־HTTPS לצורך תמיכה תקינה ב־Service Worker ובהתקנת PWA.

## 11. אבטחה ופרטיות

המערכת אינה מעבדת מידע אישי, אינה דורשת הרשמה ואינה מתקשרת עם Backend. בהתאם לכך, אבטחה מבוססת על צמצום המערכת והימנעות מתלויות מיותרות.

- אין לאסוף שם, דוא״ל, מיקום, פרטי מכשיר או נתוני שימוש.
- אין להוסיף Analytics, פרסום, מעקב או SDK של צד שלישי ללא שינוי דרישות מפורש.
- יש להגיש את האתר ב־HTTPS.
- יש לשמור תלויות מעודכנות ולבחון התראות אבטחה של חבילות.
- יש להימנע מהכנסת HTML לא מהימן או משימוש ב־`dangerouslySetInnerHTML`.
- יש להגדיר כותרות אבטחה מתאימות ב־Hosting, ככל שהספק מאפשר, כגון `X-Content-Type-Options: nosniff` ו־`Referrer-Policy: strict-origin-when-cross-origin`. מדיניות CSP יכולה להיות מצומצמת למשאבים שהאפליקציה באמת דורשת, תוך בדיקה שאינה חוסמת את קובצי ה־Build או את ה־Service Worker.
- יש להשתמש רק בקובצי אודיו עם זכויות שימוש מתאימות.
- אין מידע משתמש שיש למחוק, לגבות או להצפין בשרת.

היעדר Backend אינו מבטל את הצורך בתחזוקת תלויות, HTTPS והגדרות Hosting בטוחות.

## החלטות מרכזיות (ADRs)

### ADR-1: פונט Heebo נארז מקומית בתוך האפליקציה
**הקשר:** ה־Style Guide מגדיר את Heebo כפונט היחיד. טעינה מ־Google Fonts יוצרת תלות בשירות חיצוני בזמן ריצה, בניגוד לסעיפים 9.3 ו־11, ופוגעת בעבודה Offline (Milestone 3).
**החלטה:** הפונט נטען מחבילת `@fontsource/heebo` (משקלים 400, 600, 700), שקובצי הפונט שלה נכללים ב־Build ומוגשים מאותו דומיין של האפליקציה.
**השלכות:** אין בקשות רשת חיצוניות לפונטים; קובצי הפונט ייכללו ב־Precache ב־Milestone 3. הדפדפן מוריד רק את תת־הקבוצות (עברית/לטינית) שנדרשות בפועל.

### ADR-2: השמעת הצליל מתחילה בתוך לחיצת הכפתור, ובקר האודיו יושב ב־`App`
**הקשר:** דפדפנים (במיוחד Safari ב־iPhone) מאשרים השמעה רק כאשר `play()` נקרא ישירות בתוך פעולת המשתמש. הפעלת צליל הכניסה מתוך `useEffect` אחרי מעבר המסך עלולה להיחסם.
**החלטה:** בקר האודיו (`audioController`) נוצר פעם אחת ב־`App`. ה־handler של `Enter` קורא ל־`playEntrySound()` ורק אחר כך מחליף מסך; `Start`, עיגול ה־Play ו"הפעלת קול" קוראים ל־`play()` ישירות בלחיצה. לכל צליל אלמנט `Audio` אחד שנטען מראש ומשמש שוב; צליל חדש עוצר את הקודם, וטיימר עוצר כל השמעה אחרי שתי שניות.
**השלכות:** סיכוי גבוה יותר שההשמעה לא תיחסם; מצב האודיו (`idle`/`playing`/`blocked`/`error`) מוצג ב־React דרך `useSyncExternalStore`.

### ADR-3: קיצור קובצי הצלילים לשתי שניות בחיתוך frames
**הקשר:** `burp` (3 ש׳), `boing` (5 ש׳) ו־`bouncy-cartoon` (57 ש׳) ארוכים משתי שניות; לא מותקנים כלי עריכת אודיו (כמו ffmpeg).
**החלטה:** הקבצים קוצרו לשתי השניות הראשונות שלהם (‎1.99 ש׳) בסקריפט Node חד־פעמי שחותך frames שלמים של MP3, בלי קידוד מחדש. הקבצים המקוריים נשמרים בהיסטוריית git. בנוסף, הבקר עוצר כל השמעה בתום שתי שניות.
**השלכות:** הקבצים קטנים (כ־60KB כל אחד). יש להאזין לתוצאה — בעיקר ב־`bouncy-cartoon`, שבו ייתכן שהקטע הרצוי אינו בשתי השניות הראשונות; במקרה כזה מחליפים את הקובץ (באותו שם) או חותכים מנקודה אחרת.

### ADR-4: PWA באמצעות `generateSW` עם עדכון אוטומטי ו־Precache מפורש לאודיו ולפונט
**הקשר:** Milestone 3 דורש התקנה כ־PWA ועבודה Offline מלאה, כולל ארבעת הצלילים, בלי ערבוב בין גרסאות של קוד וקובצי אודיו (§8.2–8.3). ברירת המחדל של Workbox לא שומרת קובצי `mp3` ופונטים, ולא היה במקורות עיצוב לאייקון האפליקציה.
**החלטה:** `vite-plugin-pwa` במצב `generateSW` (ה־Service Worker נוצר אוטומטית, ללא קוד SW ידני), עם `registerType: 'autoUpdate'` ו־`cleanupOutdatedCaches`. `globPatterns` כולל במפורש `mp3`, `woff` ו־`woff2`, כך שכל קובץ ב־`dist/` נכנס ל־Precache אחד; הסקריפט `scripts/check-precache.mjs` מוודא זאת בכל `npm run test:pwa`. ה־Manifest נוצר בזמן Build (`dist/manifest.webmanifest`) מתוך `vite.config.ts`; האייקונים נוצרים מ־`public/icon-source.svg` (טבעות פסטל על Warm White — אושר על ידי בעלת המוצר) באמצעות `@vite-pwa/assets-generator`, ונשמרים בשורש `public/` (ולא ב־`public/icons/` כפי שהוצע ב־§4). ה־Service Worker פעיל רק ב־Build (`npm run start:pwa`, פורט 4173), לא בשרת הפיתוח.
**השלכות:** גרסה חדשה מורידה את כל הקבצים שלה לפני שהיא נכנסת לפעולה, ורק אז הקבצים הישנים נמחקים — נבדק: אחרי עדכון כל קובצי הגרסה החדשה ב־Cache, לא נשארו קבצים ישנים, והצלילים מתנגנים Offline. הגרסה החדשה מופיעה בפתיחה הבאה, בלי הודעה למשתמשת. ה־Precache כולל את כל תתי־הקבוצות של Heebo (כ־800KB בסך הכול) — מקובל לאפליקציה קטנה. האודיו מוגש מה־Cache כקובץ מלא (לא בבקשות חלקיות); נבדק ב־Chromium. אם תתגלה בעיה ב־Safari/iPhone, המעבר יהיה ל־`injectManifest` עם `RangeRequestsPlugin` לקובצי האודיו.

### ADR-5: פריסה ל־GitHub Pages דרך GitHub Actions, עם נתיב בסיס משתנה
**הקשר:** בעלת המוצר פרסמה ב־GitHub Pages (החלופה המותרת ב־§10.1). האתר לא עלה מסיבה כפולה: GitHub Pages הגיש את קובצי המקור מה־repo (`index.html` שמפנה ל־`/src/main.tsx`) במקום את ה־Build, והאתר מוגש מתת־נתיב (`/BreatheIn/`) בעוד שכל הנתיבים באפליקציה הניחו את שורש הדומיין.
**החלטה:** Workflow ב־`.github/workflows/deploy-pages.yml` בונה את האפליקציה בכל push ל־`main` ומפרסם את `dist/` ל־GitHub Pages (מקור ה־Pages בהגדרות ה־repo: "GitHub Actions"). נתיב הבסיס נקבע במשתנה `BASE_PATH` (ב־Workflow: `/<repo>/`); בלעדיו הוא `/`, כך שהפיתוח המקומי, הבדיקות ו־Cloudflare Pages לא משתנים. ה־`base` של Vite, `start_url`/`scope` של ה־Manifest ו־`navigateFallback` של ה־Service Worker נגזרים ממנו.
**השלכות:** אותו קוד מתאים גם לשורש דומיין וגם לתת־נתיב. נבדק מקומית Build עם `BASE_PATH=/BreatheIn/`: כל הנתיבים, ה־Service Worker וה־Cache (כולל ארבעת הצלילים) תחת `/BreatheIn/`, והזרימה Enter → Start עובדת. ה־PWA המותקן מוגבל ל־`/BreatheIn/`.

### ADR-6: סיבוב הטבעות והדיסק הלבן ב־CSS בלבד, בנפרד מכפתור ה־Play
**הקשר:** Milestone 4 דורש שהטבעות במסך הפעולה יסתובבו לאט וברציפות כל עוד המסך מוצג, בעוד שעיגול ה־Play, `Start` ו"הפעלת קול" נשארים יציבים, ובכפוף לכלל "הפחתת תנועה" (§12).
**החלטה:** חמש הטבעות נעטפו במיכל `action-screen__orbit` (ממלא את ריבוע המוטיב, `aria-hidden`), שמסתובב ב־`@keyframes` של CSS: סיבוב מלא ב־40 שניות (הואץ מ־60 לבקשת בעלת המוצר), `linear`, `infinite`, עם `will-change: transform`. כפתור ה־Play נשאר מחוץ למיכל, מעליו (`z-index`). לבקשת בעלת המוצר גם הרקע הלבן של עיגול ה־Play מסתובב: בתוך הכפתור יש דיסק לבן (`action-screen__play-disc`) עם אותה הנפשה, בעוד שהכפתור עצמו, הצל וסמל ה־Play נשארים קבועים. הדיסק לבן אחיד, ולכן הסיבוב שלו כמעט אינו נראה לעין. ל"הפחתת תנועה" לא נוסף קוד — הכלל הקיים ב־`global.css` מבטל את ה־animation, והטבעות עומדות.
**השלכות:** אין JavaScript, state או ספרייה חדשה, והתנועה לא משפיעה על האודיו או על הלחיצות. שינוי הקצב = שינוי ערך אחד ב־`ActionScreen.css`. בדיקות Playwright ב־`e2e/rings.spec.ts` מוודאות סיבוב, יציבות ה־Play ו־`Start`, הישארות בגבולות המסך והיעדר תנועה במסך הבית וב"הפחתת תנועה".
