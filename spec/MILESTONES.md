# MILESTONES.md

# אבני דרך לפיתוח — „נשום פנימה” (Breathe In)

## מטרת המסמך

המסמך מגדיר ארבע אבני דרך לפיתוח האפליקציה בהתאם ל־`PRD.md`, ל־`ARCHITECTURE.md` ול־`DESIGN.md`. כל אבן דרך מסתיימת בתוצר שניתן להריץ, לבדוק ולהציג לאישור המשתמש. אין במסמך לוחות זמנים או אומדני משך.

**גבולות המימוש:** אפליקציית Web מסוג PWA, המותאמת בראש ובראשונה למובייל, עם שני מסכים בלבד: מסך הבית ומסך הפעולה. הטכנולוגיות הן React, TypeScript, Vite, CSS או CSS Modules, HTML Audio API, `vite-plugin-pwa` ו־Workbox; אירוח ב־Cloudflare Pages. אין Backend, Database, Authentication, APIs חיצוניים, Analytics או איסוף מידע אישי. לפיכך אין צורך בסביבות Database או ב־Database Migrations.

**סדר ותלויות:** Milestone 1 ← Milestone 2 ← Milestone 3 ← Milestone 4. אין להתחיל אבן דרך לפני אישור קודמתה.

## Milestone 1 — אפליקציה עובדת ומסך הבית ✅

### שם ומטרה
הקמת בסיס אפליקציה רץ, עם מסך בית מעוצב ונגיש, בהתאם ל־Wireframes ול־Style Guide. זוהי אבן הדרך הטכנית המקדימה היחידה הנחוצה כדי לאפשר את שאר ה־Vertical Slices.

### מה יש לממש
- פרויקט React + TypeScript + Vite עם הגדרות TypeScript strict, ניהול גרסאות ב־Git ו־GitHub, וכלי בדיקה בסיסיים לפי הארכיטקטורה.
- מסך הבית בלבד במצבו הרגיל: הכותרת **„נשום פנימה”** וכפתור **`Enter`**; ללא צלילים במסך הבית.
- יישום Heebo, פלטת הצבעים, הגרדיאנטים, הריווח והכפתור בהתאם ל־`DESIGN.md`, תוך התאמה למובייל ול־RTL (`lang="he"`, `dir="rtl"`).
- שלד ניהול מצב מסך מקומי שיאפשר מעבר למסך הפעולה בהמשך, ללא הוספת Router חיצוני או מסכים שלא הוגדרו. בשלב זה כפתור `Enter` אינו נדרש להוביל למסך פעולה שטרם נבנה.

### תוצר מצופה
אפליקציה שנפתחת מקומית בדפדפן ומציגה מסך בית מעוצב, רספונסיבי וקריא; הפרויקט ניתן להרצה ולבניית Production Build.

### Definition of Done
- [ ] הפעלת הפרויקט מציגה את מסך הבית ללא שגיאות Runtime או Build.
- [ ] מופיעים רק הכותרת „נשום פנימה” וכפתור `Enter` כרכיבי התוכן המרכזיים, בהתאם ל־Wireframes.
- [ ] אין השמעת צליל בטעינת המסך או בזמן שהייה בו.
- [ ] פונט Heebo, RTL, צבעים, כפתור ופריסה תואמים למסמכי העיצוב במובייל וב־Desktop.
- [ ] `TypeScript` typecheck, `ESLint` ו־Build עוברים ללא שגיאות.
- [ ] ניתן להציג את מסך הבית למשתמש לצורך אישור חזותי לפני המשך הפיתוח.

## Milestone 2 — חוויית צלילים מלאה בשני מסכים ✅

### שם ומטרה
מימוש ה־Vertical Slice המרכזי: כניסה ממסך הבית, השמעת צליל הכניסה, והפעלת צלילים אקראיים.

### מה יש לממש
- מסך הפעולה בהתאם ל־Wireframes (ללא כפתור `Home`): מוטיב טבעות חופפות עם עיגול Play לחיץ במרכזן, וכפתור `Start`; ללא טיימר, הנחיות נשימה או מסך שלישי. העיגול עם סמל ה־Play פועל בדיוק כמו `Start`.
- מעבר ממסך הבית למסך הפעולה בלחיצה על `Enter`. אין מעבר חזרה; מסך הבית מוצג רק בפתיחה מחדש של האפליקציה.
- קטלוג של **ארבעה קובצי אודיו מקומיים**, כל אחד באורך עד שתי שניות: פלוץ (`fart`), גיהוק (`burp`), צליל קפיצי מצויר (`bouncy-cartoon`) ובוינג (`boing`). יש לוודא הרשאות שימוש מתאימות לקבצים.
- **תנאי מקדים:** ארבעת הקבצים הורדו על ידי בעלת המוצר מ־Pixabay (או Mixkit) ונשמרו ב־`src/assets/sounds/` בשמות הקבועים, עם תיעוד מקור ב־`SOURCES.md`, כמפורט ב־ARCHITECTURE סעיף 7.1.1.
- ניסיון להשמיע את צליל הפלוץ עם הכניסה למסך הפעולה; טיפול במקרים שבהם הדפדפן חוסם את ההשמעה, לרבות כפתור "הפעלת קול" עם אייקון רמקול מושתק באותו מסך, בהתאם ל־DESIGN.
- בחירה אקראית מתוך **כל ארבעת הצלילים** בכל לחיצה על `Start`, כולל אפשרות לחזרה רצופה על אותו צליל.
- טיפול בניגון חוזר, עצירת השמעה קודמת בעת הפעלת צליל חדש.
- בדיקות יחידה ב־Vitest ללוגיקת הבחירה ולמצבי השמעה, ובדיקות זרימה בסיסיות ב־Playwright.

### תוצר מצופה
אפליקציה מקומית מלאה מבחינה פונקציונלית: שני מסכים, ניווט תקין וכל ארבעת הצלילים זמינים להפעלה. אין עדיין דרישה לפעילות Offline מלאה.

### Definition of Done
- [ ] לחיצה על `Enter` מעבירה למסך הפעולה ומנסה להשמיע את צליל הפלוץ.
- [ ] מסך הפעולה מכיל רק את רכיבי ה־UI שנקבעו במקורות; לחיצה על העיגול עם סמל ה־Play פועלת בדיוק כמו `Start`.
- [ ] כל לחיצה על `Start` בוחרת אחד מארבעת הצלילים, ללא סינון הצליל האחרון; בדיקות מוכיחות שחזרות מותרות.
- [ ] כל ארבעת הקבצים זמינים מקומית, אורכו של כל קובץ אינו עולה על שתי שניות, והושגה הרשאת שימוש מתאימה.
- [ ] אם `play()` נדחה, האפליקציה אינה קורסת ומציגה באותו מסך כפתור "הפעלת קול" עם אייקון רמקול מושתק; לחיצה עליו משמיעה את הצליל.
- [ ] אין במסך הפעולה כפתור `Home` או קישור למסך הבית; במסך הבית לא מתנגן צליל.
- [ ] בדיקות Vitest ו־Playwright הרלוונטיות עוברות; נבדקה ידנית השמעה בדפדפן אמיתי, בכפוף למגבלות autoplay.
- [ ] שני המסכים נבדקו מבחינת מראה, RTL ו־Responsive, והזרימה המלאה הוצגה לאישור המשתמש.

## Milestone 3 — PWA ושימוש Offline

### שם ומטרה
להפוך את החוויה הקיימת ל־PWA שניתן להתקין בדפדפנים תומכים ולהשתמש בה ללא רשת לאחר טעינה ראשונה מלאה.

### מה יש לממש
- שילוב `vite-plugin-pwa` ו־Workbox, עם Web App Manifest, שם האפליקציה, אייקונים מתאימים ו־`display: standalone`.
- רישום Service Worker ושמירת App Shell, קובצי Build, משאבי עיצוב וארבעת קובצי האודיו ב־Precache.
- מדיניות עדכוני Cache עקבית כדי למנוע ערבוב בין גרסאות של קוד וקובצי אודיו.
- בדיקות התקנה, טעינה חוזרת, Offline והשמעת צלילים לאחר ניתוק רשת.

### תוצר מצופה
Production Build של PWA שניתן לבדוק בסביבה מאובטחת מתאימה, ושבו שני המסכים וכל הצלילים עובדים ללא אינטרנט לאחר שמירת המשאבים.

### Definition of Done
- [ ] קובץ Manifest תקין, אייקונים תקינים ו־Service Worker נרשם בהצלחה ב־HTTPS או ב־localhost נתמך.
- [ ] כל ארבעת קובצי האודיו ומשאבי האפליקציה מופיעים ב־Cache לאחר טעינה ראשונה מלאה.
- [ ] לאחר טעינה מלאה וניתוק הרשת ניתן לפתוח את האפליקציה, לנווט בין שני המסכים ולהשמיע צלילים.
- [ ] האפליקציה ניתנת להתקנה בדפדפן תומך; מגבלות התקנה של דפדפנים אחרים אינן מוצגות כתקלה במוצר.
- [ ] עדכון גרסה אינו משאיר הפניות למשאבים חסרים או משבית את ההשמעה.
- [ ] בדיקות Offline ו־PWA מתועדות ומוצגות למשתמש לאישור.

## Milestone 4 — אימות סופי ופרסום Production

### שם ומטרה
לוודא שהמוצר תואם ל־PRD, לארכיטקטורה ולעיצוב, ולפרסם גרסה נגישה ב־Cloudflare Pages.

### מה יש לממש
- בדיקות End-to-End מלאות של שני המסכים, ניווט, אודיו, שגיאות השמעה, PWA ו־Offline.
- בדיקות במובייל וב־Desktop, כולל RTL, נגישות בסיסית, ניגודיות, Focus, גדלי לחיצה ו־Responsive.
- בדיקות Build, TypeScript, ESLint, Vitest ו־Playwright; תיקון ליקויים שנמצאו במסגרת הדרישות הקיימות בלבד.
- פריסת `dist/` ל־Cloudflare Pages מתוך GitHub, עם HTTPS ונתיבי משאבים תקינים; אימות Service Worker ו־Cache בסביבת Production.
- אימות שאין תלות ב־Backend, Database, APIs חיצוניים או Analytics, ושלא נאסף מידע אישי.

### תוצר מצופה
כתובת Production פעילה לאפליקציה, עם שני מסכים מעוצבים, ארבעת הצלילים, אפשרות התקנה בדפדפנים תומכים ועבודה Offline לאחר טעינה מלאה.

### Definition of Done
- [ ] אתר Production נפתח ב־HTTPS ומציג את מסך הבית ללא שגיאות או משאבים חסרים.
- [ ] כל זרימת `Enter` → מסך הפעולה → `Start` פועלת באתר המפורסם.
- [ ] צליל הכניסה, בחירה אקראית מכל ארבעת הצלילים, חזרות מותרות וניסיון חוזר לאחר חסימה נבדקו.
- [ ] כל ארבעת הצלילים נבדקו בסביבת Production; אורכם עד שתי שניות.
- [ ] אחרי טעינה מלאה ב־Production, ניתוק הרשת אינו מונע פתיחה, ניווט או השמעת צלילים.
- [ ] המסכים תואמים ל־`DESIGN.md`; אין מסך הדרכה שלישי, טיימר או פיצ'רים שלא הוגדרו.
- [ ] בדיקות TypeScript, ESLint, Build, Vitest ו־Playwright עוברות, ותוצאות בדיקות ידניות בדפדפנים הרלוונטיים מתועדות.
- [ ] לא קיימים Backend, Database, Authentication, APIs חיצוניים, Analytics או איסוף מידע אישי.
- [ ] המשתמש קיבל קישור לאפליקציה ואת תוצאות הבדיקות לצורך אישור סופי.

## Development Execution Rules — כללי ביצוע מחייבים ל־AI

1. **יש לפתח את ה־Milestones לפי הסדר המוגדר במסמך.** אין לדלג על אבן דרך או להתחיל את הבאה לפני השלמת קודמתה.
2. **בסיום כל Milestone יש לעצור את הפיתוח.** יש להציג למשתמש את התוצר העובד, את אופן בדיקתו ואת תוצאות הבדיקות מול כל סעיף ב־Definition of Done, תוך ציון מפורש של סעיפים שלא הושלמו או לא אומתו.
3. **אין להתחיל בפיתוח ה־Milestone הבא ללא אישור מפורש של המשתמש.** אישור אינו משתמע משתיקה, מהצלחת בדיקות או מעצם השלמת התוצר.
4. אין להוסיף מסכים, פיצ'רים, רכיבים או תשתיות שלא הוגדרו ב־PRD, ב־ARCHITECTURE או ב־DESIGN. במקרה של סתירה מהותית יש להציף אותה למשתמש לפני שינוי התכנון.
5. כל אבן דרך צריכה להותיר את האפליקציה במצב שניתן להריץ ולבדוק, בהתאם לתוצר המצופה שלה. יש להפריד בין בדיקה בסביבת Development לבין אימות ב־Production באבן הדרך האחרונה.
